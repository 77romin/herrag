## 0. 요약

현행 파이프라인을 baseline으로 두고 추출·청킹·검색·프롬프트를 각각 하나씩만 바꿔가며 측정했다.
가장 크게 움직인 것은 검색 방식이었고, 가장 크게 빗나간 것은 **측정 도구 자체**였다.

| 확인한 것 | 결과 |
| :--- | :--- |
| 평가 하네스가 3문항 fallback으로 돌고 있었음 | 10문항으로 정상화 |
| ContextPrecision이 랭킹을 감지하지 못하고 있었음 | 청크 단위 전달로 수정 |
| 검색을 하이브리드로 교체 | ContextRecall 0.900 → **1.000**, ContextPrecision 0.671 → **0.819** |
| 프롬프트의 배타적 지시 분리 | AnswerRelevancy 0.537 → **0.632** |
| "유사도 점수"가 유사도가 아니었음 | 전체 점수의 **50.7%가 음수** |
| 청킹이 원인이라는 초기 가설 | **반증됨**. 다만 청크 크기는 별개로 검색에 영향 |

## 1. 실험 환경과 방법

### 1-1. 측정을 먼저 고쳤다

성능을 논하기 전에 평가 하네스에서 다섯 가지를 수정했다. 이것을 고치지 않으면
이후 모든 비교가 의미를 잃는다.

| # | 문제 | 원인 | 조치 |
| :--- | :--- | :--- | :--- |
| 1 | 10문항이 아니라 3문항으로 평가되고 있었음 | `eval_ragas.py`가 `./test_cases.json`(실행 위치 기준)을 찾는데 파일은 `servers/`에 있음 → 로드 실패 후 하드코딩 fallback | 스크립트 위치 기준 경로로 변경 |
| 2 | ContextPrecision이 랭킹을 판별하지 못함 | 청크 5개를 이어붙인 문자열 1개를 넘겨 `K=1`로 고정 | `RAGState`에 `retrieved_texts` 추가, 청크 리스트로 전달 |
| 3 | 서버 종료 시 색인 소멸 | lifespan의 `shutil.rmtree` | `KEEP_CHROMA` 환경변수로 제어, 기본 보존 |
| 4 | 임베딩 모델 설정이 무시됨 | `.env`는 `EMBEDDING_MODEL`, 코드는 `EMBEDDING_MODEL_NAME` | 키 이름 통일 |
| 5 | 검색 점수를 기록할 수 없었음 | 상태에 점수가 없음 | `RAGState`에 `scores` 추가 |

4번은 확인 결과 Chroma collection의 dimension이 **1536**이었다. `.env`에 적힌
`text-embedding-3-large`(3072)가 아니라 기본값 `text-embedding-3-small`이 쓰이고 있었다.
baseline의 재현성을 위해 실제 동작하던 small로 명시하고, large는 별도 실험 조건으로 분리했다.

### 1-2. LLM 없이 재는 검색 지표

Ragas는 LLM 심사라 같은 입력에도 실행마다 점수가 달라진다. 검색 단계의 비교에는
LLM을 쓰지 않는 결정론적 지표를 따로 만들었다.

10개 테스트 질문 각각에 대해 정답이 실제로 적혀 있는 위치를 **앵커 문자열**로 라벨링했다.
앵커는 모두 원문에서 정확히 1회만 등장하는 것으로 확인했다.

| 질문 | 앵커 |
| :--- | :--- |
| 예비군 결석 처리 | `예비군/민방위 등` |
| 경조사 공가 일수 | `본인 결혼 (5일)` |
| 지각·조퇴 누적 | `지각/조퇴/외출 3회` |
| 정규 교육시간 | `09:00 ~ 18:00` |
| 휴대전화·외부음식 | `외부 음식 반입 및 취식 금지` |
| 명찰 재발급 비용 | `16,500` |
| 캠퍼스 보안 반입 | `봉인` |
| 수료 기준 | `6회 이상 Pass` |
| 장학 지급 | `Job-Fair 시작 후 3~4주차` |
| 지각·조퇴 체크 시각 | `18:30` |

이 라벨로 **Recall@k**와 **MRR**을 계산했다. 같은 입력이면 항상 같은 값이 나온다.

| `SSAFY_GUIDE.md` (기본 제공) | 9,153 | 232 | 25 | 77 | 615자 |

(5,000만원 vs 8,000만원)이 다르다.** 비슷하면서 다른 숫자가 섞여 있어 검색 정밀도를
시험하기에 적합하다.

## 2. F207 ① 수집한 문서에 적합한 내용 추출 방식

### 2-1. 문제 관찰

`SSAFY_GUIDE.md`는 표 안에 `<br>` 태그로 항목을 욱여넣은 구조다. `<br>`이 116개 있고,
그 결과 **한 줄이 최대 615자**에 이른다. 마크다운 표의 파이프(`|`)는 292개,
`&nbsp;` 엔티티와 백틱 강조도 본문에 그대로 섞여 있다.

`RecursiveCharacterTextSplitter`의 구분자는 `["\n\n", "\n", ".", " ", ""]`이다.
`<br>`은 개행이 아니므로 분할기 입장에서 이 615자는 **끊을 곳이 없는 한 덩어리**다.

### 2-2. 세 가지 표현 비교

같은 내용을 세 가지 형태로 두고 검색 품질을 측정했다.

| 표현 | 설명 | 문자수 | 청크 | 최장 줄 |
| :--- | :--- | ---: | ---: | ---: |
| `md_raw` | 현행. 마크업이 그대로 | 9,153 | 30 | 615자 |
| `txt_plain` | 제공된 평문판. `<br>`이 실제 개행으로 풀림 | 7,592 | 18 | 95자 |
| `md_norm` | 직접 작성. `<br>`→개행, 엔티티 제거, **표 헤더를 각 행에 주입** | 8,258 | 24 | 95자 |

**결과 (10문항, MRR)**

| 표현 | dense | BM25 | hybrid |
| :--- | ---: | ---: | ---: |
| `md_raw` (현행) | 0.742 | 0.867 | 0.850 |
| `txt_plain` | 0.708 | 0.850 | **0.933** |
| `md_norm` (내가 만든 것) | 0.734 | 0.750 | 0.800 |

### 2-3. 해석

**평문판이 하이브리드 검색에서 가장 좋았다** (MRR 0.933, Recall@1 0.90). `<br>`이 실제
개행으로 풀리면서 분할기가 항목 경계에서 자를 수 있게 됐고, 청크가 18개로 줄면서
각 청크가 하나의 주제를 온전히 담게 된 것으로 보인다.

**직접 만든 정규화는 실패했다.** 표 헤더를 각 데이터 행 앞에 붙이면 맥락이 살아날 것으로
기대했으나 BM25가 0.867에서 0.750으로 떨어졌다. 헤더 단어("구분", "주요 내용", "비고")가
모든 행에 반복 삽입되면서 문서 전체에서 흔한 토큰이 되었고, 질문과의 변별에 기여하지
못한 채 각 청크의 유효 정보 밀도만 낮춘 것으로 해석한다.

**적용 결론**: 마크다운 표를 그대로 임베딩하지 말고 평문으로 펴는 편이 낫다. 다만
"맥락을 더 넣으면 좋아진다"는 직관은 이 문서에서 성립하지 않았다.

## 3. F207 ② 문서에 따른 청킹 방식

### 3-1. 초기 가설과 반증

명찰 질문(`교육 명찰을 분실했을 때는 어떻게 해야 하나요? 재발급 비용이 있나요?`)에서
ContextRecall과 ContextPrecision이 모두 0이었다. 표가 615자짜리 한 줄인 것을 보고
**"분할기가 표를 잘라 재발급 비용이 소실되었을 것"** 이라고 가설을 세웠다.

분할 결과를 직접 확인해 이 가설을 **반증**했다.

```
총 청크 30개 / 길이 min 40, median 340, max 492 / 500자 초과 0개

정답 청크 #16 (401자) — 온전함
  ## 4. 보안 규정
  ### 4-1. 교육장 입·출문 보안규정
  ...
      * 교육 명찰 분실 시 즉시 신고 및 분실 사유서 작성 후 재발급
          * ※ 재발급 비용 약 16,500원 본인 부담
      * 재발급 기간 동안 임시 교육 명찰 패용 (당일 반납 원칙)
```

정답은 헤더까지 포함해 401자 청크 안에 온전히 들어 있었다. 청크는 멀쩡했고,
**검색이 그 청크를 상위로 올리지 못한 것**이 원인이었다.

### 3-2. 청크 크기 격자 실험

가설은 틀렸지만 청크 크기 자체는 별개로 영향이 있었다.

| 설정 | 청크 수 | dense MRR | BM25 MRR | hybrid MRR | dense R@5 | hybrid R@5 |
| :--- | ---: | ---: | ---: | ---: | ---: | ---: |
| recursive-300 | 49 | **0.867** | 0.750 | 0.808 | 0.90 | 1.00 |
| recursive-500 (현행) | 30 | 0.742 | 0.867 | 0.850 | 0.90 | 1.00 |
| recursive-1000 | 13 | 0.646 | 0.883 | 0.775 | 0.90 | 1.00 |
| markdown-500 (헤더 주입) | 30 | 0.645 | 0.883 | 0.850 | **1.00** | 1.00 |

**명찰 질문의 정답 청크 순위**

| 설정 | dense 순위 |
| :--- | ---: |
| recursive-300 | **1위** |
| recursive-500 (현행) | 6위 |
| recursive-1000 | 3위 |
| markdown-500 | 3위 |

### 3-3. 해석

**청크가 작을수록 dense 검색이 좋아진다** (MRR 0.646 → 0.742 → 0.867). 청크가 크면
여러 주제가 한 벡터로 평균되면서 특정 질문에 대한 변별력이 떨어진다. 300자로 줄이자
명찰 질문의 정답이 6위에서 1위로 올라왔다.

그런데 **BM25는 반대 방향**이다 (0.750 → 0.867 → 0.883). 키워드 매칭은 청크가 클수록
관련 단어를 더 많이 포함해 유리하다.

두 방향이 상쇄되어 **하이브리드는 500자에서 가장 좋았다** (0.850). 즉 최적 청크 크기는
문서만으로 정해지지 않고 **어떤 검색 방식을 쓸 것인지에 함께 달려 있다.**

헤더 주입(markdown-500)은 dense MRR을 0.742에서 0.645로 떨어뜨렸지만
Recall@5는 0.90에서 **1.00**으로 올렸다. 평균 순위는 나빠지고 최악의 경우는 개선되는,
방향이 엇갈리는 변화였다.

## 4. F207 ③ 평가 시스템을 이용한 성능 개선

### 4-1. 검색 방식 비교

`recursive-500` 고정, 세 가지 검색 방식.

| 방식 | R@1 | R@3 | R@5 | MRR |
| :--- | ---: | ---: | ---: | ---: |
| dense (현행) | 0.60 | 0.80 | 0.90 | 0.742 |
| BM25 단독 | 0.80 | **1.00** | **1.00** | 0.867 |
| hybrid (RRF, 0.5/0.5) | 0.70 | **1.00** | **1.00** | 0.850 |

명찰 질문에서 dense는 6위였으나 **BM25는 1위**였다. 정답 청크에만 있는
"명찰 / 재발급 / 16,500 / 분실" 같은 고유 키워드를 정확히 잡아낸 결과다.
`rank_bm25`는 `requirements.txt`에 이미 있었으나 코드에서 쓰이지 않고 있었다.

한국어 조사 처리를 위해 별도 토크나이저를 시험했으나, **공백 분리만으로도 이미 1위**였다.
조사 분리 토크나이저는 같은 토큰을 중복 삽입해 점수를 0.47에서 8.52로 부풀렸을 뿐
순위를 바꾸지 못했다. 채택하지 않았다.

### 4-2. 임베딩 모델 교체

`text-embedding-3-small`(1536) → `text-embedding-3-large`(3072).

| 모델 | dense MRR | dense R@5 | dense R@10 | 명찰 질문 순위 |
| :--- | ---: | ---: | ---: | ---: |
| small | 0.742 | 0.90 | **1.00** | 6위 |
| large | 0.788 | 0.90 | 0.90 | **23위** |

전체 MRR은 0.742에서 0.788로 올랐지만, **명찰 질문은 6위에서 23위로 추락**했고
Recall@10이 1.00에서 0.90으로 떨어졌다. 차원을 두 배로 늘린 모델이 특정 질문에서는
오히려 크게 나빠졌다. 비용이 두 배 이상인 점을 감안하면 채택할 근거가 없다.

### 4-3. 프롬프트 수정

현행 프롬프트의 마지막 줄이 문제였다.

```
[참고문서]에 없는 내용은 '문의 사항은 참고 문서에 없습니다.' 라고만 답하세요.
```

복합 질문에서 문서에 일부만 근거가 있을 때, 모델이 **정상 답변을 다 쓰고 나서 이 문구를
뒤에 덧붙였다.**

> **A(현행)**: 예비군 훈련은 국가 관련 소집으로 공가로 처리됩니다. … 장기간 부재는 교육
> 담당자와 사전 면담 필요 **문의 사항은 참고 문서에 없습니다.**

| 프롬프트 | 거절 문구 등장 | 단독 거절 | **정상 답변 뒤에 덧붙음** |
| :--- | ---: | ---: | ---: |
| A 현행 | 3 / 10 | 1 | **2** |
| B 수정 | 0 / 10 | 0 | 0 |

수정판은 배타적 지시를 항목별 규칙으로 분리했다. "질문의 **어떤 항목도** 문서에서 찾을 수
없을 때에만" 거절하고, 일부만 확인되면 확인된 것을 먼저 답한 뒤 나머지에 대해서만
없다고 밝히도록 했다.

### 4-4. Ragas 종합 평가 (10문항 × 3회 반복)

LLM 심사는 실행마다 흔들리므로 각 조건을 3회 반복해 평균±표준편차로 보고한다.

| 조건 | Faithfulness | AnswerRelevancy | ContextRecall | ContextPrecision |
| :--- | ---: | ---: | ---: | ---: |
| **A** 현행 | 0.954 ± 0.031 | 0.537 ± 0.027 | 0.900 ± 0.000 | 0.671 ± 0.005 |
| **B** 프롬프트만 수정 | 0.941 ± 0.052 | **0.632 ± 0.014** | 0.900 ± 0.000 | 0.666 ± 0.028 |
| **C** 하이브리드 + 프롬프트 | 0.967 ± 0.016 | 0.565 ± 0.019 | **1.000 ± 0.000** | **0.819 ± 0.005** |

**A 대비 변화량**

| 조건 | Faithfulness | AnswerRelevancy | ContextRecall | ContextPrecision |
| :--- | ---: | ---: | ---: | ---: |
| B | −0.013 (노이즈) | **+0.094 (유의)** | ±0.000 | −0.005 (노이즈) |
| C | +0.012 (노이즈) | +0.028 (노이즈) | **+0.100 (유의)** | **+0.149 (유의)** |

유의 판정 기준: 변화량이 표준편차의 2배를 넘고 절대값이 0.05 이상일 때만 유의로 본다.

### 4-5. 해석

**조치와 지표는 깔끔하게 대응했다.** 프롬프트만 고친 B는 AnswerRelevancy만 올렸고
검색을 건드리지 않았으므로 ContextRecall이 정확히 그대로였다(0.900, 표준편차 0.000).
검색을 바꾼 C는 ContextRecall과 ContextPrecision을 올렸다.

**Faithfulness는 세 조건 모두 노이즈 범위였다.** 표준편차가 0.016~0.052로 가장 크고
변화량은 0.013 이하였다. 이 지표로는 어떤 주장도 하기 어렵다.

**주의할 점 하나.** C의 AnswerRelevancy(0.565)는 B(0.632)보다 낮다. 같은 프롬프트인데
검색 결과가 달라져 답변이 달라졌기 때문이다. 검색을 개선했다고 모든 지표가
함께 오르지는 않는다.

## 5. F208 ① 업로드한 문서에 따른 AI 응답 변화

질문·모델·프롬프트를 고정하고 **참조 가능한 문서만** 바꿨다.

| 상태 | 조건 |
| :--- | :--- |
| S1 | RAG 끄기 (모델의 사전지식만) |
| S2 | RAG 켜기, 규정집만 색인 |
| S3 | RAG 켜기, 청년월세 문서 업로드 후 |

### 5-1. 질문: "국토교통부 청년월세 한시 특별지원은 최대 몇 개월 동안 총 얼마까지 받을 수 있나요?"

**S1 (RAG 끄기)**
> 과거 사례: 한시성 청년 월세 지원은 흔히 **3~6개월** 범위로 지급된 경우가 많고, 총액은
> 지자체·정책에 따라 **수십만 원에서 100만원대**까지 차이가 있었습니다.

**S2 (규정집만)**
> 문의 사항은 참고 문서에 없습니다.

**S3 (문서 업로드 후)**
> 국토교통부 청년월세 한시 특별지원은 최대 **24개월**간, 총 **480만원**(월 최대 20만원)까지
> 받을 수 있습니다.

### 5-2. 관찰

**S1의 답은 그럴듯하지만 틀렸다.** "3~6개월, 100만원대"는 실제(24개월, 480만원)와
크게 다르다. 모델은 확신 없는 표현("~인 경우가 많고")을 섞어 정중하게 답했지만,
그 정중함이 오답을 걸러주지는 않았다.

**S2는 정직하게 거절했다.** 세 질문 모두 "참고 문서에 없습니다"로 답했다. 관련 문서가
없을 때 지어내지 않는 것이 RAG의 실질적 이득이다.

**S3는 문서의 숫자를 그대로 답했다.** 세 사업의 보증금·월세 요건을 묻는 질문에도
8,000만원/60만원(서울)과 5,000만원/70만원(국토부)을 정확히 구분해 답했다.

### 5-3. 그런데 오염도 관찰됐다

"인천에 사는 37세 청년인데 어디에 신청해야 하나요?"에 대한 S3 답변:

> 만 35세~39세 구간에 해당하므로 인천시 자체 사업으로 접수합니다.
> 인천청년포털 온라인 신청 또는 행정복지센터 방문하여 신청하세요.
> **문의: 청년월세지원센터 1833-2030 / 다산콜센터 120**

앞 두 문장은 정확하다. 그러나 마지막 줄의 두 번호는 문서에서 **서울시 절(3-5)에만**
적혀 있다. 인천 질문의 답변에 서울 연락처가 딸려 들어왔다. 검색된 5개 청크 안에
서울 절이 섞여 있었고, 모델이 그것을 같은 맥락으로 취급한 결과다.

## 6. F208 ② 유사도 기준과 문서 분할 방식이 결과에 미친 영향

### 6-1. "유사도 점수"는 유사도가 아니었다

`similarity_search_with_relevance_scores`가 돌려주는 점수를 전수 확인했다.

```
collection.metadata = None          ← hnsw:space 미지정
전체 점수 범위: -0.3070 ~ 0.3967
음수 비율: 50.7%
Chroma 경고: UserWarning: Relevance scores must be between 0 and 1
```

원인은 거리 척도다. Chroma는 `hnsw:space`를 지정하지 않으면 **L2**를 쓴다.
langchain-chroma는 L2일 때 `1 − d/√2` 변환을 적용하는데, `d > √2`인 문서에서
결과가 음수로 떨어진다. 전체 점수의 절반이 여기에 해당했다.

**중요한 확인**: `hnsw:space`를 `cosine`으로 바꾸면 점수는 0~1로 정상화되지만
**순위는 한 건도 바뀌지 않는다.** 단위 벡터에서 L2 거리와 코사인 유사도는 단조 관계이므로
정렬 결과가 동일하다. 10문항 전체에서 두 방식의 순위가 완전히 일치함을 확인했다.

> 즉 거리 척도 수정은 **점수를 해석 가능하게 만드는 조치이지 검색 품질 개선이 아니다.**

### 6-2. 임계값을 올리면 정답이 먼저 죽는다

| threshold | 통과 청크 평균 | 정답 통과 질문 | **정답 차단 질문** |
| ---: | ---: | ---: | ---: |
| 0.00 | 14.8 | 10 | 0 |
| 0.05 | 10.7 | 10 | 0 |
| 0.10 | 7.4 | 10 | 0 |
| 0.15 | 4.9 | 10 | 0 |
| 0.20 | 2.4 | 8 | **2** |
| 0.25 | 1.5 | 7 | **3** |

질문별 1위 점수와 정답 점수의 차이는 대부분 0.00~0.02로 붙어 있고, 가장 벌어진
경우가 0.108이다. 점수의 동적 범위가 좁아 **노이즈만 걸러내는 임계값이 존재하지 않는다.**

### 6-3. 임계값과 k는 서로를 대체하지 않는다

threshold 0.15에서 평균 4.9개가 통과하고 정답은 10문항 모두 통과한다. 그런데
명찰 질문의 정답은 그 시점에도 **6위**다. 즉 임계값을 통과했지만 `k=5`에 잘린다.

| k | 정답 포함 | 컨텍스트 길이 |
| ---: | ---: | ---: |
| 3 | 8 / 10 | 약 1,020자 |
| 5 (현행) | 9 / 10 | 약 1,700자 |
| 8 | **10 / 10** | 약 2,720자 |
| 10 | **10 / 10** | 약 3,400자 |

**임계값은 점수가 낮은 것을 걸러낼 뿐 순위를 바꾸지 못한다.** 정답을 top-k 안으로
올리는 일은 검색 방식이 해야 한다. 하이브리드는 `k=5`에서 10/10을 달성했다(4-1절).

### 6-4. 분할 방식의 영향

3장에서 측정한 대로, 청크 크기는 dense와 BM25에 반대 방향으로 작용한다.
현행 500자는 dense 단독으로는 최적이 아니지만(300자가 MRR 0.867로 더 좋음)
하이브리드 기준으로는 500자가 가장 좋다(0.850). 분할 방식은 검색 방식과 분리해서
결정할 수 없다.

## 7. F208 ③ RAG 방식의 장점과 한계

이 프로젝트에서 실제로 관측한 것만 적는다.

### 7-1. 장점

**모르는 것을 모른다고 답하게 만든다.** S1에서 모델은 "3~6개월, 100만원대"라는 그럴듯한
오답을 냈지만, S2에서는 세 질문 모두 거절했다. 근거를 문서로 한정하면 지어내기가 줄어든다.

**출처를 표시할 수 있다.** 답변마다 어떤 파일에서 왔는지 붙일 수 있고, 실제로 S3의
답변은 `YOUTH_RENT_GUIDE.md`를 출처로 표시했다. 사용자가 검증할 수 있는 형태가 된다.

**문서 교체만으로 도메인이 바뀐다.** 모델도 프롬프트도 코드도 그대로 두고 파일 하나를
올리자 답변이 "모른다"에서 정확한 수치로 바뀌었다.

### 7-2. 한계

**밀집 벡터는 고유 키워드의 변별력을 희석한다.** "명찰·재발급·16,500"이 정답 청크에만
있는데도 dense 검색은 6위로 밀어냈다. 상위에는 "교육명찰 상시 패용", "명찰 임의 대여 금지"처럼
같은 단어를 공유하는 다른 규정이 올라왔다. 의미를 벡터로 압축하는 과정에서 특정 숫자와
고유명사의 식별력이 사라진다.

**유사도 점수로 품질을 판정할 수 없다.** 점수의 절반이 음수였고, 1위와 정답의 차이가
0.02 안에 들어오는 질문이 대부분이었다. 임계값을 올리면 노이즈보다 정답이 먼저 잘렸다.
"유사도 0.7 이상이면 관련 있다" 같은 규칙은 이 시스템에서 성립하지 않는다.

**검색된 이웃이 답변을 오염시킨다.** 인천 질문의 답변에 서울시 연락처가 딸려 들어왔다.
컨텍스트에 함께 들어온 다른 절의 정보를 모델이 같은 맥락으로 취급했다. 검색이 정답을
가져와도 **함께 가져온 것들이 답을 오염**시킬 수 있다.

**환각 방지 지시가 정상 답변을 훼손한다.** "문서에 없으면 없다고만 답하라"는 지시는
복합 질문에서 정상 답변 뒤에 거절 문구를 덧붙이게 만들었다(10문항 중 2건).
안전장치가 그 자체로 결함이 된 사례다.

**"더 좋은 모델"이 항상 더 좋지 않다.** 임베딩을 large로 바꾸자 전체 MRR은 올랐지만
명찰 질문은 6위에서 23위로 떨어졌다. 평균만 보면 개선이지만 특정 질문에서는 파국이다.

**평가 도구도 조용히 틀린다.** 청크를 이어붙여 넘기는 바람에 ContextPrecision이
랭킹을 전혀 감지하지 못하는 상태로 오래 돌아가고 있었다. 지표가 숫자를 뱉는다고
그 숫자가 의미 있는 것은 아니다.

## 8. F208 ④ 추가로 개선 가능한 부분

시간 관계로 적용하지 않았으나 근거가 있는 것들을 적는다.

**검색 실패 시 일반 응답으로 분기.** F206은 "검색 결과가 없으면 일반 AI 응답임을 명시"하라고
요구한다. 6-2절에서 확인했듯 점수 임계값으로는 판정할 수 없으므로, **BM25 점수가 0이면서
상위 점수와 정답 후보의 격차가 작을 때**를 실패로 보는 편이 낫다. LangGraph에 조건부
엣지 하나를 더하면 구현된다.

**재순위화(reranker).** 하이브리드로 Recall@5는 1.00이 되었지만 Recall@1은 0.70이다.
정답을 1위로 올리려면 cross-encoder 재순위화가 필요하다. 다만 CPU 환경에서 질문당
2초 내외의 지연이 예상되어 이번 범위에서는 보류했다.

**응답 스트리밍.** 현재는 생성이 끝날 때까지 화면이 멈춘다. `StreamingResponse`와
LangGraph의 `.stream()`으로 토큰 단위 출력이 가능하다. 체감 응답성이 크게 달라진다.

**클라이언트 오류 처리.** `script.js`가 `response.ok`를 확인하지 않아 서버가 4xx/5xx를
반환하면 `data.answer`가 `undefined`인 채 말풍선에 출력된다. `.catch`는 네트워크 단절만
잡는다. F201의 "서버 오류 시 안내" 요구를 충족하려면 상태 코드 분기가 필요하다.

**검색 근거의 UI 노출.** 서버 콘솔에는 이미 검색된 청크와 점수가 출력된다. 이것을
화면에 접어서 보여주면 사용자가 "AI가 무엇을 보고 답했는지" 직접 확인할 수 있다.
이 프로젝트의 목적(데이터가 응답에 미치는 영향의 이해)에 가장 부합하는 개선이다.

**관측 도구 도입.** LangSmith는 이미 의존성으로 설치되어 있어 환경변수만으로
retrieve→generate 호출 트리, 단계별 지연, 토큰 수를 볼 수 있다. 다만 문서 본문과 질문이
외부 서비스로 전송되므로 대외비 자료를 다룰 때는 판단이 필요하다.

```
experiments/
  corpus/YOUTH_RENT_GUIDE.md        직접 수집한 두 번째 문서

  run_extraction.py                 추출 방식 3종 비교
  run_ragas_ab.py                   A/B/C 조건 Ragas 평가 (RUN_ID로 반복)
  run_document_ab.py                문서 교체 전/후 응답 비교
  aggregate.py                      3회 반복 평균±표준편차 집계
  results/                          모든 측정 결과 (json/csv)
```

```bash
cd C:\SSAFY\chatbot-project_lab
servers\.venv\Scripts\python.exe experiments\run_retrieval.py
servers\.venv\Scripts\python.exe experiments\run_threshold.py
servers\.venv\Scripts\python.exe experiments\run_extraction.py
servers\.venv\Scripts\python.exe experiments\run_document_ab.py
for %R in (1 2 3) do set RUN_ID=%R && servers\.venv\Scripts\python.exe experiments\run_ragas_ab.py

```

임베딩은 `results/_emb_cache.json`에 캐시되므로 재실행 시 추가 API 호출이 발생하지 않는다.
